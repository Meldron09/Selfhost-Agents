# MCP connection config comes from pinned MCP Registry entries, not hand-authored schemas

Each curated MCP server (currently GitHub and n8n — a Microsoft 365 connection was researched and deferred, see CONTEXT.md's Auth Mode entry) needs a schema describing what credentials a Connection requires — which fields, which are secret, which are required. Rather than hand-authoring and maintaining that schema ourselves, we read it from the official MCP Registry (registry.modelcontextprotocol.io), whose `server.json` format already declares exactly this (env vars/headers/args, each flagged `isRequired`/`isSecret`). Both agent-chat-ui (to render the auth window's fields) and deepagent-aegra (to know what to store and hand to the MCP client) treat a pinned Registry Entry as the source of truth.

We pin each Connection to one specific, verified server name (`io.github.github/github-mcp-server`) rather than resolving by live search or letting the person pick from search results: the Registry is open to anyone to publish to, and a live search for "github" or "sharepoint" surfaces many low-quality or unrelated third-party entries alongside the real one — confirmed in practice while researching a (since-deferred) Microsoft 365 pin, where several dead or credential-less entries turned up under "teams"/"sharepoint" search terms. Pinning trades away auto-discovery of new servers for reliability of the ones we've chosen to support.

**Amendment (n8n):** a server with no public Registry listing — n8n, which is a self-hosted instance at a per-deployment URL — gets a hand-authored `server.json` in the same shape, checked in next to the fetched ones. The schema stays the single source of truth for credential fields, so agent-chat-ui and deepagent-aegra need no second code path; the rule becomes "pinned, and hand-authored only when there is no Registry entry to pin". Since n8n's URL differs per instance, it is declared in the entry as a non-secret field the person fills in, not a constant.
