# MCP connections persist across runs, unlike web-search's per-run gate

ADR-0007 established that a capability toggles per run via `configurable`, read by a middleware (`WebSearchGateMiddleware`) that gates delegation — the subagent is always structurally registered, only its usability flips per request. MCP Connections deliberately do **not** follow that precedent: connecting a server (GitHub, SharePoint, Microsoft Teams) is a one-time action in agent-chat-ui's Settings surface, and once enabled, its tools stay available on every subsequent run until switched off there — not re-toggled per message.

We chose this because a Connection requires real setup (credentials, sometimes an interactive Device Code sign-in) that `web-search` never needed — `TAVILY_API_KEY` is a deployment-wide secret already present before any run, so a per-run boolean was enough. MCP credentials have nowhere to live before this feature: they're stored in a new Connection Store, a small local encrypted-at-rest file (not a database or secrets manager — this stack has neither, and remains single-user/self-hosted, not multi-tenant). A future reader used to ADR-0007's per-run pattern should not "fix" MCP toggling to match it; the two capabilities have different lifecycles by design.

## Consequences settled while designing the `mcp` subagent

- **Where the store lives.** The Connection Store sits in its own `MCP_STATE_DIR` on its own named volume, never under `FILE_STORE_DIR`: the `/files/{key}` route serves anything resolvable under that root, so credentials there would be downloadable. The same separation argument as ADR-0002.
- **Encryption.** The file is Fernet-encrypted; the key comes from the `MCP_STORE_KEY` env var, checked lazily (only when the store is first touched), so the stack still boots for people who never use MCP. A key kept in a file beside the ciphertext was rejected: same volume, so it would protect almost nothing. A wrong key or corrupt file is a loud error, never a silent reset to empty.
- **Lifecycle granularity.** The `ClientGroup` lives per `task` delegation, not per agent run: a `CompiledSubAgent` has no run-level hook, and moving the tools onto the orchestrator would defeat a single `mcp` subagent.
- **Write tools need human approval.** Connections act on the person's real accounts and nothing else in this stack is approval-gated. Every MCP tool whose server annotations do not declare `readOnlyHint: true` is gated with `HumanInTheLoopMiddleware` (approve/reject, per call), on the inner agent built after tools are listed. Unannotated tools are gated (fail-closed). The gate is always on and independent of `REQUIRE_APPROVAL`; that flag stays inert.
- **A retry after an approved write re-prompts.** On resume the `mcp` runnable re-runs (re-reads the store, reconnects, re-lists) and the inner agent continues from its checkpoint. But the orchestrator's `ToolRetryMiddleware` wraps `task` by name and cannot exclude `mcp` alone, so if the inner agent fails transiently *after* an approved write ran, the retry restarts it from scratch and raises a fresh approval for the replayed write. Accepted: the replay is re-gated and never silently duplicated, at the cost of a second prompt. Revisit only if it shows up in real use.
- **Enabled-set changes mid-approval drop the pending call.** The gate is rebuilt from the fresh store read and tool list on resume, so a Connection disabled or removed while the person decides never has its pending call auto-executed: a disabled one gets the "nothing was run, action dropped" reply, a removed one leaves a tool name the inner agent refuses as not valid.
