# Attachment acknowledgment via a `wrap_model_call` middleware, not a synthetic message

`attachments` (agent/state.py) is a custom LangGraph state field, declared alongside `outputs` per ADR-0001. Unlike `outputs`, which only ever needs to reach `agent-chat-ui` (a post-run state fetch, per ADR-0001), `attachments` also needs to reach the orchestrator's own model call — CONTEXT.md's Orchestrator definition requires it to acknowledge every received Attachment by name in its first reply, as the mitigation for LangGraph's silent-drop-on-unrecognized-state-key behavior. A custom state field is never part of `state["messages"]`, so nothing puts it in front of the model unless something does so explicitly.

`AttachmentAcknowledgeMiddleware` (agent/attachment_ack.py) does this via `wrap_model_call`/`awrap_model_call`: on every orchestrator model call, it reads `request.state["attachments"]` and, if non-empty, rewrites `request.system_message` to append a note listing each Attachment's filename and key, then calls through. Passed to `create_deep_agent(middleware=[...])`, this only ever touches the orchestrator's own model calls — source-level inspection of the installed `deepagents`==0.7.4 package (`deepagents/graph.py`) confirms top-level `middleware=` is not inherited by declarative `SubAgent` specs (`file-reader`, `output-writer`), each of which builds its own middleware stack from scratch in `create_deep_agent`'s subagent-processing loop.

**Rejected**: inserting a synthetic `HumanMessage`/`SystemMessage` into `state["messages"]` (via `before_model`, or as part of the state update itself) naming the attachments. Rejected because it would need to track whether that note had already been inserted for a given run (to avoid inserting a fresh acknowledgment message on every one of the orchestrator's turns within the same run), and because a `wrap_model_call` rewrite is naturally per-call and stateless: it recomputes the note fresh from current `state["attachments"]` every time rather than trying to reconcile a permanent message against a list that (via `operator.add`) can grow across a thread's later turns.

Confirmed against the real middleware surface by source-level inspection: `AgentMiddleware.wrap_model_call`'s default implementation raises `NotImplementedError` when the graph is invoked asynchronously (`ainvoke`/`astream`) and only a sync override is defined — `aegra serve` and tests/test_server_compat.py's blockbuster guard both invoke asynchronously, so `AttachmentAcknowledgeMiddleware` implements `awrap_model_call` too, not only `wrap_model_call`.

## Known limitation: `attachments` is thread-scoped, not run-scoped

Because `attachments` uses `operator.add` (mirroring `outputs`, per ADR-0001's own reasoning), an Attachment from turn one of a thread is still in `state["attachments"]` on turn five — the middleware has no way to tell "new this run" from "seen already" apart from the list's own accumulated contents, so it surfaces every Attachment on every call. Two consequences, addressed at different layers on purpose rather than by adding tracking state to solve both mechanically:

- The note's wording says "available in this thread", not "received this run", so it stays accurate once it's no longer describing only the current turn.
- Delegation discipline (don't re-send `file-reader` an Attachment it already read, unless asked to re-read it) is left to `agent/graph.py`'s SYSTEM_PROMPT, not enforced in code. A code-level fix (e.g. a second state field tracking which Attachment keys have already been delegated) was considered and rejected as disproportionate to this ticket's scope: it would need its own reducer, its own middleware or tool-side bookkeeping, and its own tests for what is fundamentally a prompt-following question, not a plumbing one — the middleware's job is limited to making `attachments` visible, not to deciding what the orchestrator does with that visibility.
