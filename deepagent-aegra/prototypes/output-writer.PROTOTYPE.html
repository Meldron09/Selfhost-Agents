output-writer subagent — tool signatures, storage convention, system prompt

Question this demo is checking (wayfinder ticket #5, map #1): output-writer is the reverse of file-reader (issue #4) — structured data goes in, a file comes out — and it produces an Output ({key, filename}, per ADR-0001) instead of consuming one. The crux design question: with OutputsGuardMiddleware and the outputs/-as-shown-directory convention (agent-runtime's pattern) explicitly dropped for this project, does output-writer need any directory convention at all? This prototype's answer: no — each write tool serializes its structured input to bytes, hands them to store_output_bytes(filename, bytes) (the write-side mirror of file-reader's resolve_attachment_bytes(key), backed by the same upload/download HTTP app), gets back an opaque key, and returns {key, filename} — the tool never touches a path, and there's nothing for a "shown directory" to be, since discovery is entirely through the outputs state field. Each tool also picks its own filename extension rather than trusting a caller-supplied one, so there's no extension-mismatch failure mode to design for. Click through the scenarios below, or free-play. The pure module in the <script> block is what would lift into deepagent-aegra/agent/subagents/output_writer.py — same shape, Python instead of JS, real libraries (openpyxl/python-docx/python-pptx) instead of mocked bytes, and a real tool return of Command(update={"outputs": [...]}) instead of a mocked state list.
